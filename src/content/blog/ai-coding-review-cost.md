这周看到一组数据，愣了一下。

哈佛的学者追踪了 700 多家引入 AI 编程 Agent 的软件企业，结论挺反直觉的：代码提交量涨了 20% 到 30%，PR 数量多了 23%，但衡量真实产出的 Jira 任务完成率几乎没变。PR 从提交到合并的周期反而拉长了 49%，被打回修改的比例接近翻倍。

另一头，BairesDev 调查了 705 名开发者：AI 平均每周帮人省下 13 小时编程时间，听着很美好。但 67% 的人说，审查 AI 生成代码花的时间反而变多了。

省下的时间没有消失，只是换了个地方被花掉。

## 瓶颈不在生产端，在验证端

这事细想不难理解。以前代码是稀缺品，写得慢，看得过来。现在 AI 十几分钟能吐出几千行，而一个人一分钟吃透一个函数已经算快。生产端加了马达，验证端还是两条腿走路，堵是必然的。

更麻烦的是 AI 代码读起来更累。读同事写的代码，你能大概猜到他为什么这么写。AI 的代码没有"为什么"，只有结果。它还特别擅长局部最优：眼前这个问题解得很漂亮，但完全没有全局架构意识，一个模块一个模块堆上去，几个迭代之后就是一座没人敢动的代码山。

还有个隐蔽的坑是测试同源。AI 既写实现又写测试，两边可能错在同一个地方。测试全绿，看着很安心，实际上边界情况根本没人真的读过。

## GitHub 的服务器也在替这笔账买单

审查只是人的成本，机器的成本也在涨。

GitHub 披露，2026 年已经新增了 400 万 CPU 核心和 160 PB 存储。背景是：今年 9 月，开发者和 Agent 在平台上产生了 73.8 亿次提交，是去年同期的五倍多（数据来自[腾讯云开发者社区的整理](https://cloud.tencent.com.cn/developer/article/2775072)）。

这里面有个很真实的场景：配置粗糙的 Agent 改个空格就推一次，报错换个变量名再推一次，把 GitHub Actions 当远程调试器用。一晚上功能没交付多少，git log 翻出几十页。每一次"再试一下"背后都是一轮环境初始化、依赖安装和自动化测试。个人省下的等待，变成团队共享 Runner 的排队。

## 那到底该怎么用

我不觉得结论是"别用 AI 写代码"，那也太因噎废食了。但这几份调查放在一起，指向的做事方式其实挺清楚：

审查要分流，别一视同仁。文案、样式、低风险改动，交给自动化测试和静态扫描就够了。涉及权限、支付、用户数据的改动，必须人来逐行看。逐行通读所有 AI 产出在生产环境里根本不可持续，承认这一点是第一步。

Agent 要有"本地验证"的门槛。能在提交前跑完的检查就别推到 CI 上去跑，同类失败达到上限就停下来等人介入，而不是无限重试。这是协作礼貌，也是成本控制。

考核指标得换。如果团队还拿提交次数和代码行数衡量产出，Agent 会轻松把数字做得很漂亮，交付原地踏步。值得追踪的是另一组数：一个需求经过几次无效重试、消耗多少 CI 分钟、审查者理解改动花了多久、上线后返工了没有。

写代码这件事正在变便宜，变贵的是判断"这段代码该不该合进去"。这个趋势短期内看不到回头，早点适应比焦虑有用。
